### 0.4. Настоящие причины `database is locked`
- `POST /api/grouping/regroup` по умолчанию регруппирует **все бренды одной транзакцией** (`api/groups.py:61-63,136-138`) → коммит на бренд, как в рантайме.
- Каждая правка группы (`_apply`, `api/groups.py:443-450`) уже ограничена брендом (`regroup([brand_id], full=True)` + пересчёт метрик бренда), но для Balenciaga (286k объявлений) это всё равно длинная транзакция. Сначала замерить время правки на Balenciaga; если > 3 с — переводить правку на инкрементальный путь (существующий `regroup --delta` / переназначение только объявлений затронутых групп + пересчёт метрик только затронутых `scope_key`).
- API-записи не координируются с `_write_lock` парсера → одна обёртка «mutation» с ретраем на `OperationalError: database is locked` (3 попытки, экспоненциальная пауза) для всех API-мутаций.
- CLI-движки (`cli.py:59,121,220,246,292,330`) обходят listener прагм → `foreign_keys=OFF`, нет `busy_timeout`. Использовать общую фабрику движка из `db/session.py`.
- На подключении добавить `PRAGMA journal_size_limit = 67108864`; после фазы метрик прогона — `PRAGMA wal_checkpoint(TRUNCATE)` и `PRAGMA optimize`.

### 1.1. Планировщик (D3)
- **Где:** новый `backend/app/services/scheduler.py`, запуск в lifespan `backend/app/main.py`. Без APScheduler (тест `test_project_config.py:40` запрещает зависимость; противоречие с `docs/ROADMAP.md:4` разрешается в пользу отсутствия зависимости — обновить ROADMAP).
- **Логика:** asyncio-цикл проверяет каждые 10 мин: включён ли план, нет ли активного прогона (`market_lock`), был ли успешный плановый прогон в текущем слоте (`schedule_hour`, по умолчанию 04:00 локального времени). Если слот пропущен (MacBook спал или был выключен) — догоняющий запуск при пробуждении/старте. По воскресеньям — `full: true` (sold-инкремент с перекрытием 2 ч теряет поздно проиндексированные продажи; `LIFECYCLE.md` обещает недельный full).
- **Настройки** (`app_settings`, страница Settings): `schedule_enabled` (по умолчанию `false`), `schedule_hour`, `schedule_brand_ids` (по умолчанию все бренды с данными), `schedule_rpm` (по умолчанию 90 — прогон без присмотра идёт с комплаенс-дефолтом).
- **Остановка на троттлинге:** ≥ 3 подряд 429/WAF по задачам прогона → прогон прерывается со статусом `partial`, план ставится на паузу на 6 ч, событие в лог. Сейчас падает только задача (`client.py:295-300`) — это нарушает правило CLAUDE.md «stop on repeated 429».
- **Обслуживание после прогона:** checkpoint/optimize (см. 0.4). Раз в неделю после full: `db-backup` → `retention --apply`. Ротация бэкапов по количеству (хранить 3 последних) и удаление сайдкаров `-shm`/`-wal` (сейчас glob берёт только `*.sqlite3`). VACUUM — только вручную, новой CLI-командой `db-vacuum`, с проверкой свободного места ≥ 2× размера БД и остановленного приложения.
- **Опционально:** `launchd`-агент (`~/Library/LaunchAgents/…plist`) для автозапуска приложения при логине — описать в `docs/OPERATIONS.md`, не обязательно.

## 5. Фаза 2 — математика ликвидности (≈ 5–7 дней)

Новые модули (маленькие файлы): `backend/app/services/metrics/supply.py`, `liquidity.py`, `seasonality.py`, `fees.py`; формулы — чистые функции с юнит-тестами. Константы — именованные, в начале модуля.

### 2.1. Предложение: сырое, эффективное, свежее
- `active_now` — как сейчас.
- **Спящий оптовик** продавца `s` в бренде `b`: `active(s,b) ≥ 200` и `sold_365(s,b) / (sold_365(s,b) + active(s,b)) < 1%`.
- `active_effective` = активные без лотов спящих оптовиков и без флагов replica/lot.
- `active_fresh` = `active_effective` с `max(created_at, bumped_at) ≥ as_of − 60 дн`.
- Это **не** отклонённый фильтр майнинга оптовиков (`config/grouping.yaml`, 2026-10-08): группировка не меняется, меняется только знаменатель предложения. UI показывает сырое и эффективное значение рядом.

### 2.2. P30 — вероятность продажи за 30 дней (главная метрика скорости)
- Когорта `C` = объявления (корни цепочек репостов, дата старта — дата корня) с `created_at ∈ [as_of − 120 дн, as_of − 30 дн]`, без флагов replica/lot, без спящих оптовиков.
- `P30 = |{l ∈ C : sold_at − created_at ≤ 30 дн}| / |C|`.
- **Сглаживание к родителю** (эмпирический Байес): `P̃30 = (k + m·p_parent) / (n + m)`, `m = 20`, `p_parent` — P30 типа товара внутри бренда, затем типа по всем брендам. Базовый уровень по всей когорте (на уровне цепочек, без спящих оптовиков) = **13,8%** (8 047 / 58 200; с оптовиками было бы 5,7%). Пример: модель с 1 продажей из 1 → `(1 + 20·0,138)/21 ≈ 0,18` (а не 100%); GAT с 402 из 1 051 → `≈ 0,378`.
- **Известное смещение:** удалённые до 2026-10-06 лоты (до начала наблюдений) не попали в БД → знаменатель занижен → P30 завышен. Исчезает, когда планировщик накопит 120 дней наблюдений (≈ 2027-02). До этого метрика помечается «β».

### 2.3. Цена и торг (вместо Ask-to-Bid)
- Ведро состояния: `new` (`is_new`) / `used` (остальные). Все ценовые метрики — по ведру и общие.
- `gmv_90d = Σ sold_price` (без флагов replica/lot/outlier).
- `offer_discount = median(1 − sold_price / ask_last)` по продажам 90 дней.
- `total_markdown = median(1 − sold_price / price_initial)` (нужен 0.1).
- `fresh_ask_premium = median(ask по active_fresh, ведро) / median(sold_price 90 дн, ведро) − 1` — это и есть блок «Ask vs Sold» в UI.
- `days_at_final_price = median(sold_at − price_updated_at)` — как быстро вещь уходит, когда цена правильная (заменяет эвристику «Clean Days»).
- Медианы показываются только при n ≥ 5 продаж в ведре, иначе — значение родителя с пометкой «≈».

### 2.4. Liquidity Score 0–100
> **Заменено 2026-10-16 (liquidity-v2, `docs/METRICS.md` §3).** Заказчик выбрал простой рейтинг из четырёх показателей — продажи за 30 дней, скорость продажи, лайки и цена — с порогом входа; `trend_score` удалён. Пункт ниже оставлен как история решения.

- **Опорная выборка раздела** `Q(section)` = модели раздела с `retired_at IS NULL` и `sold_90d ≥ 5`. Если в `Q` меньше 20 моделей — берётся опорная выборка по всем разделам; гистерезис: раздел переходит на собственную выборку при |Q| ≥ 22 и возвращается к общей при |Q| < 18 (bags сейчас ≈ 20 — без гистерезиса LS прыгал бы между пересчётами), а использованная опора пишется в `group_metrics.ls_ref_scope` и показывается в тултипе. Почему: по всем моделям p95 `sold_90d` = 2–7 (tops 3, outerwear 2, dresses 0) — нормировка по ним не ранжирует и для dresses даёт `ln(1) = 0` в знаменателе.
- Компоненты:
  - `V = min(1, P̃30 / P30_ref)`, `P30_ref` = p95 `P̃30` по `Q`;
  - `D = min(1, ln(1 + sold_90d) / ln(1 + sold_ref))`, `sold_ref` = p95 `sold_90d` по `Q`.
- Защита: если `ref ≤ 0` (или `ln(1 + ref) = 0`) — компонент = 0 и группа получает «Мало данных»; пересчёт никогда не падает.
- `LS = 100 · V^0.6 · D^0.4` (взвешенное геометрическое среднее: нулевая глубина обнуляет оценку — ловушка «одна редкая продажа» закрыта и сглаживанием V, и малым D).
- GMV как третий компонент — только если бэктест (2.7) покажет прирост ρ: `G ≈ D × цена`, а `ln(·)^0.2` почти константа. Веса меняются только по бэктесту. `trend_score` остаётся как метрика роста.
- Все перцентили разделов (LS, бейджи 3.5, снапшоты 1.3) считаются только по группам с `retired_at IS NULL` — 1 650 строк `group_metrics` принадлежат retired-группам с замороженными метриками.

### 2.5. Сезонность
- Считается на уровне **типа товара** (`product_type` × `department`), по всем брендам; внутри бренда — только если у типа ≥ 600 продаж/год. Модель наследует профиль своего типа; если у модели ≥ 300 продаж/год — смесь с весом `w = n/(n + 300)`.
- Только полные месяцы (первый и последний месяц данных отбрасываются).
- `SI_abs(t,m) = sales(t,m) / mean_m(sales(t,m))` — абсолютный профиль (когда продаётся больше всего).
- `SI_rel(t,m) = [sales(t,m)/Σ sales(t)] / [sales(all,m)/Σ sales(all)]` — относительно всей площадки (убирает общий декабрьский пик и артефакты покрытия сбора).
- Сезон (осень = сен–ноя, зима = дек–фев, весна = мар–май, лето = июн–авг) = среднее трёх месяцев; показывается только при ≥ 50 продажах типа в сезоне.
- **Прогноз «что закупать сейчас на сезон X»:** `ожидаемые продажи 30д в X = текущие sold_30d × SI_abs(t, X) / SI_abs(t, окно)`, где `SI_abs(t, окно)` — среднее профиля по полным месяцам, которые пересекаются с последними 30 днями; если таких нет (так будет весь октябрь 2026: октябрь 2025 неполный, октябрь 2026 идёт) — среднее соседних полных месяцев (сентябрь и ноябрь).
- Ограничение при D1 = «копить»: один год не отделяет сезонность от тренда бренда — в UI подпись «профиль по 1 году». При ≥ 24 месяцах — сравнение профилей год-к-году (корреляция; при ρ < 0,5 профиль помечается нестабильным).

### 2.6. Калькулятор ресейлера (логика бэкенда, UI — в 3.4)
- `config/fees.yaml`: ступени комиссии, процессинг домашний/международный, дата вступления; источник — Grailed Help Center (сверить перед релизом).
- Вход: цена закупки `B`, входящие расходы `T_in` (доставка/пошлина), ведро состояния, размер (опционально).
- Выход `E` = p50 продаж 90 дней в ведре, консервативный `E_c` = p25.
- Доставка: `ship_buyer` — сколько платит покупатель (медиана `sold_shipping_price` группы или ввод), `label_cost` — реальная стоимость отправки (ввод).
- `fees(E) = max(1.99, c(E)·(E + ship_c)) + p·(E + ship_buyer) + 0.49`, где `c(E) = 9%` при `E ≥ 120`, иначе 6%; `ship_c = ship_buyer`, если не используется Grailed Label, иначе 0; `p` = 3,49% или 4,99%. Базу порога $120 (`E` или `E + ship`) сверить с Help Center при заполнении `fees.yaml` и вынести в параметр `tier_base`.
- `net = E + ship_buyer − fees(E) − label_cost`; `ROI = net / (B + T_in) − 1`.
- Ожидаемый срок продажи по P̃30 (постоянная интенсивность): `λ = −ln(1 − P̃30) / 30`, `E[T] = clamp(1/λ, 7, 365)` дней (до clamp: `P̃30 ≥ 0,999` → `E[T] = 7`, `P̃30 ≤ 0` → `E[T] = 365`; иначе `ln(0)` / деление на 0 у крошечных родителей) — честнее, чем `median_days_to_sell`, который видит только проданные. `ROI_30 = ROI · 30 / E[T]`; риск «зависания» = `1 − P̃30`; разброс цены = `IQR / p50`.

### 2.7. Бэктест — ворота приёмки для каждой новой оценки
- CLI `metrics-backtest --as-of-days 30`: считает оценки на момент `T = now − 30 дн` только по данным ≤ T (продажи с `sold_at ≤ T`; предложение ≈ `created_at ≤ T` и (active или `sold_at > T`)), сравнивает с фактическими продажами группы в `(T, now]`.
- Две цели, потому что метрики разной природы:
  - **объём** — фактические продажи группы в `(T, now]`: на нём проверяются `D` и `LS` против базовых `sold_30d` и `trend_score`;
  - **скорость** — доля предложения на момент T, проданная в `(T, T+30]` (forward sell-through): на нём проверяется `P̃30` против `sell_through_30d`. Сравнивать P30 с объёмом нельзя — rate против count, P30 заведомо «проиграет» и ложно заблокирует 3.5/4.1.
  - Обе цели используют одну функцию `supply_at(T)` (`created_at ≤ T` и не продан/не удалён до T — включая лоты, удалённые после T), чтобы определения предложения не разошлись.
- Метрика: Spearman ρ по группам с ≥ 5 объявлениями, `retired_at IS NULL`; отчёт — в `eval/metrics/backtest-<date>.md`.
- Известное ограничение: удалённые лоты до начала наблюдений неизвестны (то же смещение, что в 2.2).

### 2.8. Размеры
- В разбивку `sizes` добавить P30 по размеру (по той же когорте) и пометку «ходовой» (P30 размера ≥ P30 группы и ≥ 10 объявлений). Данные уже есть, это расширение `calculator.py:153-178`.

## 9. Ответы на архитектурные вопросы
- **SQLite на 22 бренда:** прогноз по фасетам нужен до сбора (1.2); по текущей плотности 1–1,5 млн объявлений ≈ 5–7 ГБ с `raw_json` — в пределах возможностей SQLite при предвычисленных метриках (`group_metrics`, `group_month_stats`). Блокировки — от длинных транзакций (0.4), не от объёма. В WAL читатели не блокируют писателя; риск — рост WAL при долгих чтениях, закрывается checkpoint после прогона и `journal_size_limit`.
- **Лимит Algolia 1000:** уже решён разбиением по `id` (`range_split`); остаточные риски — тавтологичное покрытие (0.5), гонка «проба → выборка» при росте бакета (мелко), перекрытие sold-дельты 2 ч (недельный full в 1.1).

## 12. Ревизия v1.1 (самоатака, поправки поверх разделов выше)
- **2.1 порог оптовика проверен на данных:** правило `active ≥ 200 и ST < 1%` отсекает 52 пары «продавец × бренд» = 240 314 активных (63% всех активных) при всего 537 их продажах за год. Значит, эффективное предложение — обязательная метрика, а не опция.
- **2.2 P30 — на уровне цепочки репостов:** исход «продано ≤ 30 дн» засчитывается, если **любое** звено цепочки продано в течение 30 дней от создания корня (иначе снятый корень + проданный репост считается непроданным).
